# AnyQ

ИИ-агент, который проверяет документ требований финтех-проекта до разработки: нарезает его
на отдельные требования, проверяет каждое и весь набор по критериям ISO/IEC/IEEE 29148 и
IEEE 830, задаёт автору уточняющие вопросы и пишет отчёт на русском.

## Быстрый запуск

Нужен [Rust](https://rustup.rs) (stable). Python и [uv](https://docs.astral.sh/uv/) нужны
только для разработки: мера качества и пример внешнего харнесса.

1. **Ключ модели.** Зарегистрируйтесь в [Anthropic Console](https://console.anthropic.com),
   создайте ключ в разделе *API Keys*.
2. **Куда положить.** `cp .env.example .env` и впишите ключ в строку `ANTHROPIC_API_KEY=`.
   Файл `.env` в git не попадает.
3. **Прогон одной командой:**

   ```bash
   make review IN=путь/к/требованиям.pdf OUT=reports/отчёт.md
   ```

   Команда собирает агента и проверяет документ одним процессом. Отчёт ляжет в файл `OUT`;
   папки создаются сами. Вход — `.pdf` (с текстовым слоем), `.md` или `.txt`.

Без `make`: `cargo run --release -p anyq-server -- review <требования> <отчёт.md>`.
Флаги: `--interactive` — сначала задать вопросы автору в терминале и учесть ответы;
`--json <файл>` — сохранить ещё и всю проверку в JSON; `--config <файл>` — другой конфиг.

**Модель:** `claude-opus-5-5` через API Anthropic, задаётся в `anyq.example.toml`. Чтобы
сменить модель или подключить локальную (Ollama, vLLM, llama.cpp — любой сервер с
OpenAI-совместимым API), скопируйте конфиг в `anyq.toml` и поправьте секцию `[providers]`:
команда берёт `anyq.toml`, если он есть.

Прогон на документе организаторов занимает четыре–пять минут (в четырёх измеренных прогонах
от 4 мин 11 с до 4 мин 42 с); часть вызовов модели идёт параллельно. Готовые отчёты по нему лежат в `reports/`: `card-alerts.md` — вход
Markdown (`eval/cases/card-alerts/spec.md`), `card-alerts-pdf.md` — тот же текст свёрстанным
PDF (`spec.pdf`; место там — страница и строка на странице).

## Что в отчёте

Отчёт следует шаблону организаторов. Первая строка — итог: вердикт и число требований и
дефектов. Разделы пронумерованы: паспорт прогона (документ, дата, модель, коммит агента, время
анализа), как агент нарезал требования, проверка каждого требования, проверка набора, вопросы
автору, сводка таблицей, итог и приложение «как проверялось».

У каждого требования показана цитата и строка отметок по критериям: ✅ — дефекта нет, ⚠️ —
дефект описан ниже. Отметку ставит код, а не модель. Вердикт из трёх состояний тоже считает
код: «Нельзя» — есть критичные дефекты, «Условно» — критичных нет, но есть существенные,
«Можно» — иначе. Вопросы автору пронумерованы (В-1…) и называют требование, из которого выросли.

Отброшенное не пропадает: замечание к набору, слитое с замечанием к требованию, показано в разделе 4 ссылкой на это требование, а критерий набора остаётся с ⚠️. Опровергнутые критиком замечания перечислены в приложении; полный список с причинами — в выгрузке `--json`, поле `report.dropped`.

Каждое замечание привязано к месту в тексте: модель приводит дословную цитату, код находит её
в документе и сам ставит раздел и номер строки. Замечание, цитату которого найти не удалось,
в отчёт не попадает. Критичные и существенные замечания второй проход модели пытается
опровергнуть; что не проверялось, помечено в отчёте.

## Как устроено

```
anyq-server review ─┐                     ┌─▶ встроенный конвейер (Rust): нарезка → проверка
HTTP API /v1 ───────┴─▶ ReviewService ────┤    каждого и набора → слияние → критик → отчёт
                        (состояние)       └─▶ внешний харнесс по HTTP (любой язык)
                                  все вызовы модели ─▶ шлюз ─▶ облачный API или локальный сервер
```

- `crates/core` — домен, порты, жизненный цикл проверки, шлюз моделей. Без ввода-вывода.
- `crates/pipeline` — конвейер: `src/lib.rs` — порядок этапов, `agent.toml` — промпты и
  лимиты, `criteria.toml` — критерии с постоянными id, `src/document.rs` — поиск цитат и
  якоря, `src/lint.rs` — пустые разделы и заглушки без модели, `src/report.rs` — отчёт.
- `crates/adapters` — провайдеры моделей и внешний харнесс; `crates/server` — HTTP API, CLI, конфиг.
- `eval/cases/` — эталонный кейс; `scripts/eval.py` считает пропущенные дефекты.
- `harness/` — пример внешнего харнесса на Python (`baseline`), подключается секцией `kind = "http"`.

Подробно — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), план и решения —
[docs/FOUNDATION.md](docs/FOUNDATION.md).

### Веб-интерфейс

Нужен ещё [Node.js](https://nodejs.org) 18+. В двух терминалах:

```bash
make server   # API на 127.0.0.1:8080; ключ берёт из .env, конфиг — anyq.toml или пример
make web      # интерфейс на http://localhost:5173
```

Загрузите файл ТЗ — через несколько минут будет итог: вердикт готовности, замечания с цитатами в
тексте документа, вопросы автору на полях. Ответы на вопросы отправляют документ на
перепроверку. Если порт 8080 занят, поменяйте `listen` в `anyq.toml` и запустите
интерфейс как `ANYQ_API=http://127.0.0.1:<порт> make web`. Проверки хранятся в памяти
сервера и пропадают при его перезапуске.

API — `POST /v1/reviews` (харнесс `dialog` задаёт вопросы автору), схема —
`GET /openapi.json`. Внешний харнесс `baseline` — `make harness`.

## Разработка

`make check` — формат, линтеры, тесты Rust и Python, сквозной прогон на поддельной модели.
Мера качества на эталонном кейсе:

```bash
cargo run --release -p anyq-server -- review eval/cases/card-alerts/spec.md /tmp/r.md --json /tmp/r.json
python3 scripts/eval.py eval/cases/card-alerts /tmp/r.json
```

В кейсе 19 размеченных дефектов и 14 ожидаемых вопросов автору — решений, которые за автора
не примет никто. Вопросы составил вслепую отдельный агент, который видел только документ:
без ответов нашего агента. Один вопрос агента засчитывается не больше чем за один ожидаемый.
Модель отвечает по-разному от прогона к прогону, поэтому считается медиана трёх прогонов.
На версии промптов `2026-11-27.3`:

| Мера | Медиана | Прогоны |
|---|---|---|
| Пропущено дефектов | 0 % | 0 %, 0 %, 0 % |
| Пропущено ожидаемых вопросов (все вопросы отчёта) | 0 % | 0 %, 0 %, 0 % |
| Пропущено ожидаемых вопросов среди 12 главных | 28,6 % | 28,6 %, 50 %, 28,6 % |
| Вопросов в отчёте | 26 | 20, 26, 26 |

Вопросы упорядочены по важности, повторы слиты; первые 12 — главные, их же задаёт диалог.
Строка про 12 главных считается по первым 12 вопросам отчёта тем же сопоставлением, что и
остальные меры (`evaluate` из `scripts/eval.py`); отдельного режима в скрипте нет. Жёсткий
потолок в 12 вопросов проверялся раньше и отклонён: пропуск вопросов вырос до 35,7 %, дефектов
до 5,3 %. Меры выше относятся к входу Markdown: скрипт сопоставляет по номерам строк Markdown, поэтому PDF-отчёт
`reports/card-alerts-pdf.md` кейсом не измерен. Это один кейс, а не набор: на других документах качество не измерено. Список
ожидаемых вопросов составлен моделью и человеком не сверен.
