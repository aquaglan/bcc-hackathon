# Архитектура AnyQ

## Схема

```
 веб-интерфейс, CLI, бот, CI
            │  HTTP: /v1/reviews …
            ▼
 ┌──────────────────────────── anyq-server (Rust) ────────────────────────────┐
 │  api       HTTP API, токен, OpenAPI                  crates/server             │
 │  core      жизненный цикл проверки, порты (трейты)   crates/core   без I/O     │
 │  adapters  реализации портов                         crates/adapters           │
 └───────┬───────────────────────▲──────────────────────────────┬────────────────┘
         │ шаг проверки          │ вызов модели                 │
         │ POST …/step           │ POST /v1/llm/complete        ▼
         ▼                       │                     облачный API или локальный
 ┌──── harness-сервис (Python) ──┴───┐                 сервер моделей (Ollama, vLLM,
 │  harnesses/baseline, …            │                 llama.cpp — OpenAI-совместимый)
 │  логика агента и промпты          │
 └───────────────────────────────────┘
```

Два процесса. **Сервер на Rust** — всё, что должно быть надёжным и одинаковым для любых
агентов: API, состояние проверок, доступ к моделям, ключи. **Harness-сервис на Python** — то,
что меняется десять раз в день: логика агента и промпты.

## Почему так

- **Harness — сменная часть.** Harness — это один способ вести проверку: шаг получает ТЗ и
  историю вопросов-ответов и возвращает либо новые вопросы, либо отчёт. Сервер знает только
  этот протокол, поэтому рядом с `baseline` можно поставить harness на графе, на нескольких
  агентах или на другом языке и сравнить их на одном ТЗ: имя harness — поле запроса.
- **Модель — только через шлюз.** Harness не знает, какая модель отвечает. Провайдер
  выбирается в `anyq.toml`; переход с облачного API на модель внутри контура банка — это
  смена `default_provider`, код агента не меняется. Ключи живут только в процессе сервера.
- **Ядро без ввода-вывода.** `core` описывает правила (когда проверка ждёт ответов, что
  считать ошибкой) и порты. Компилятор не даст ядру зависеть от HTTP или базы: в его
  `Cargo.toml` их нет. Поэтому правила проверяются тестами за миллисекунды.
- **Работа в фоне.** Вызов модели длится от секунд до минут, поэтому `POST` сразу отвечает
  `202`, а клиент опрашивает статус. Интерфейс не висит, соединения не рвутся по таймауту.

## Прогон одной командой

`anyq-server review <требования> <отчёт.md>` (`make review IN=… OUT=…`) — второй вход в тот же
`ReviewService`, что и HTTP-обработчики, в одном процессе. Он читает файл (PDF — постранично
через `pdf-extract`, Markdown и текст — как есть), ведёт проверку до `done`, пишет отчёт.
`--interactive` берёт харнесс `dialog` и задаёт вопросы в терминале. Ключ — из окружения или
`.env`, конфиг — `anyq.toml` или `anyq.example.toml`.

## Встроенный конвейер (`crates/pipeline`)

Порядок этапов задаёт код (`src/lib.rs`), промпты и лимиты — данные (`agent.toml`), критерии —
`criteria.toml` с постоянными id. Модель вызывается через шлюз ядра; ввода-вывода в крейте нет.
Подключается секцией конфига `kind = "pipeline"` (`ask_first = true` — режим диалога).

| Этап | Кто | Что делает |
|---|---|---|
| Нарезка | модель | требования с дословной цитатой; код находит каждую цитату в тексте и нумерует `R-..` по порядку |
| Проверка требований | модель, пачками параллельно | каждое требование по критериям 29148 п. 5.2.5 |
| Проверка набора | модель, одновременно с предыдущим | противоречия, полнота, связь частей, чек-лист организаторов |
| Верификация | код | цитата замечания найдена в тексте, иначе замечание отброшено; замечания с цитатой об одном месте и критерии слиты, замечания об отсутствующем тексте остаются критику; всё, что снято как повтор или опровергнуто критиком, остаётся в `report.dropped` с причиной, местом оставшегося замечания и доводом критика |
| Критик | модель | пытается опровергнуть критичные и существенные: опровергнутые убраны, сомнительные — вопросы автору |
| Пустые места | код (`src/lint.rs`) | строка-заглушка по словам-маркерам из `agent.toml`, раздел без текста, таблица без заполненных строк; код считает места до критика: замечание модели о таком месте критику не показывается и считается подтверждённым (решение 31); где модель места не назвала, код добавляет свой существенный `SET-COMPLETE` |
| Вопросы | модель | сливает вопросы всех этапов об одном решении и упорядочивает по важности; код не теряет ни одного исходного и отбрасывает выдуманные; первые `main_questions` — главные, их задаёт диалог |
| Отчёт | код (`src/report.rs`) | разделы по заданию организаторов, итог одной строкой в начале, отметка ✅/⚠️ по каждому критерию каждого требования, сводка таблицей; вердикт из трёх состояний: «Нельзя» — есть критичные, «Условно» — критичных нет, есть существенные, «Можно» — иначе; вопросы автору нумеруются В-1… и называют требование; замечание к набору, слитое с замечанием к требованию, показано в разделе 4 ссылкой на требование, критерий набора получает ⚠️; опровергнутые перечислены в приложении, в счёт дефектов отброшенные не входят |

Вызов модели при любой ошибке повторяется один раз; второй сбой завершает прогон ошибкой.

Место в тексте (раздел, страница, строка) всегда ставит код (`src/document.rs`): модель говорит,
что цитирует, а не где. В свёрстанном PDF нет разметки заголовков: раздел, названный моделью,
принимается, только если строка с таким текстом стоит выше цитаты. Что отброшено и почему,
перечислено в отчёте. В режиме диалога ответы автора идут во все этапы как данные рядом с
документом.

Мера: `scripts/eval.py` сравнивает проверку с разметкой кейса (`eval/cases/*/expected.toml`)
и считает две потери: «пропущено дефектов, %» и «пропущено ожидаемых вопросов, %» (вопросы
отчёта и всех раундов диалога). Замечания и вопросы вне разметки выводятся для человека.

## Жизненный цикл проверки

```
POST /v1/reviews ─▶ running ──шаг──▶ awaiting_answers ──POST …/answers──▶ running ─▶ … ─▶ done
                       │                                                               └▶ failed
                       └── шаг вернул отчёт сразу ─────────────────────────────────────▶ done
done ──POST …/answers на вопросы отчёта──▶ running   (перепроверка с ответами)
```

`running` — идёт шаг harness. `awaiting_answers` — в последнем раунде есть вопросы автору;
пустой список ответов означает «пропустить». `failed` — harness или модель вернули ошибку,
текст в поле `error`. Сколько раундов задавать, решает harness (`MAX_ROUNDS` в `baseline`).
Ответы на вопросы готового отчёта открывают новый раунд из `report.open_questions`, и
проверка идёт заново; здесь нужен хотя бы один ответ.

## API

| Метод | Назначение |
|---|---|
| `POST /v1/reviews` | начать проверку: `{spec: {title, text}, harness?}` → `202` и проверка |
| `GET /v1/reviews` | список проверок, новые сверху: заголовок, статус, число замечаний |
| `GET /v1/reviews/{id}` | статус, раунды вопросов и ответов, отчёт |
| `GET /v1/reviews/{id}/progress` | ход идущего шага: этап, сколько требований проверено, найденное до перепроверки, лента событий (≤50); только у встроенного конвейера, иначе `404`; живёт в памяти процесса |
| `POST /v1/reviews/{id}/answers` | ответы на вопросы текущего раунда или готового отчёта → `202` |
| `POST /v1/documents?name=` | тело — файл `.pdf`/`.md`/`.txt` (до 20 МБ) → `{title, text}` для `POST /v1/reviews` |
| `POST /v1/llm/complete` | шлюз к моделям для harness: `{provider?, model?, system?, messages, json_schema?}` |
| `GET /openapi.json` | полная схема API |
| `GET /health` | проверка, что процесс жив |

Ошибки: `{code, message}` с кодами 400, 401, 404, 409, 422 (модель отказала или ответ
обрезан), 502 (провайдер недоступен). Если задана переменная `ANYQ_API_TOKEN`, все `/v1`
требуют `Authorization: Bearer <токен>`. По умолчанию сервер слушает только `127.0.0.1`.

## Веб-интерфейс (`web/`)

Клиент HTTP API на React и TypeScript, без своей логики проверки (решение 24 `FOUNDATION.md`).
Путь: загрузка файла (`POST /v1/documents`) → ход проверки (опрос `…/progress` раз в секунду)
→ итог: вердикт, шкала готовности с прогнозом «после N правок», замечания с цитатами,
подсвеченными в тексте, вопросы на полях → ответы (`POST …/answers`) и перепроверка.
Прогноз считается тем же правилом, что и вердикт отчёта: критичные → «рано», существенные →
«с оговорками». «Принять правку» и черновики ответов хранятся только в браузере
(`localStorage`); документ не меняется. Шрифты собраны в бандл: внешних запросов нет.
Сборка и тесты — в `make check` (`check-web`).

## Точки расширения

| Что подключить | Что сделать |
|---|---|
| Ещё один OpenAI-совместимый сервер или облако | секция `[providers.<имя>]` с `kind = "openai_compat"` в конфиге — без кода |
| Провайдера с собственным API | `impl LlmProvider` в `crates/adapters/src/llm/` + вариант `ProviderConfig` |
| Новый harness на Python | класс с `step` в `harnesses/`, строка в `HARNESSES`, секция `[harnesses.<имя>]` |
| Harness на другом языке или готовом фреймворке | любой сервис, отвечающий на `POST` с `StepRequest` → `StepResult`; только секция в конфиге |
| Базу данных вместо памяти | `impl ReviewStore` в `crates/adapters/` и подстановка в `config.rs` |
| Интерфейс, бота, проверку в CI, вебхук | клиент HTTP API; сервер не меняется |
| Новый формат входа (docx и т. п.) | ветка в `read_document` в `crates/server/src/cli.rs`: файл → текст |

## Осознанные упрощения

Помечены в коде комментарием `shortcut:`:

- проверки хранятся в памяти процесса и пропадают при перезапуске;
- шаг выполняется задачей внутри сервера: при перезапуске проверка останется в `running`;
- ответы моделей не передаются потоком: один вызов должен уложиться в 600 секунд;
- запись ответов не атомарна: две одновременные отправки могут обе пройти;
- ответ модели, не прошедший схему, переспрашивается один раз (`Run::ask`); после второго сбоя шаг падает целиком.

Не сделано: инструменты (tool use) в шлюзе, потоковая выдача статуса (SSE), Docker-образы, CI.
