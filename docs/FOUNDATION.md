# Фундамент AnyQ

Черновик для обсуждения. Это проект: что строим, в каком порядке и по каким правилам.
Что уже написано и работает, описано в `ARCHITECTURE.md`. Решения приняты (раздел 11);
реализация идёт в порядке раздела 12.

## 1. Принципы

1. **Ни одного утверждения без доказательства.** Замечание ссылается на место в ТЗ, ссылка на
   норму — на фрагмент из базы знаний. Чего нельзя доказать, то не попадает в отчёт.
2. **Сомнение превращается в вопрос.** Если проверка не может ни подтвердить замечание, ни
   опровергнуть, оно уходит автору вопросом. Так уточняющие вопросы появляются не «по
   вдохновению модели», а из измеримой неопределённости.
3. **Сначала измерение, потом агент.** Набор ТЗ с известными дефектами и метрики строятся до
   промптов. Любое изменение агента — это изменение чисел, а не ощущений.
4. **Знания — это данные, а не код.** Шаблон ТЗ, чек-листы и нормы лежат файлами с версиями.
   Шаблон организаторов (25.11) подключается как данные, без переписывания агента.
5. **Харнесс не знает ни модели, ни агента.** Агент — это описание (промпт, инструменты,
   ограничения). Модель — строка в конфиге. Поэтому один и тот же агент потом переносится в
   чужие харнессы.
6. **Текст ТЗ — недоверенные данные.** Он может содержать инструкции для модели. Он всегда
   передаётся как данные, а инструменты агента не имеют опасных побочных действий.

## 2. Слои

```
 клиенты: веб-интерфейс, CLI, чужие харнессы (через MCP и skills)
───────────────────────────────────────────────────────────────────────────────
 API и состояние (Rust)   проверки, раунды вопросов, журнал событий, версии
───────────────────────────────────────────────────────────────────────────────
 конвейер проверки        разбор → требования → проверки → верификация → отчёт
 (порядок этапов)                                   ▲ уточнение у автора
───────────────────────────────────────────────────────────────────────────────
 харнесс                  цикл «модель ↔ инструменты», бюджет, пауза, журнал
 агенты                   описания: промпт + инструменты + ограничения
───────────────────────────────────────────────────────────────────────────────
 знания (RAG)             индекс ТЗ · нормы и шаблон · правила-чек-листы
───────────────────────────────────────────────────────────────────────────────
 шлюз моделей (Rust)      текст, инструменты, эмбеддинги; облако или on-premise
───────────────────────────────────────────────────────────────────────────────
 измерение                эталонный набор · метрики · пороги · сравнение прогонов
```

Харнесс и конвейер — разные вещи. **Харнесс** исполняет одного агента: даёт модели инструменты
и ведёт цикл. **Конвейер** задаёт порядок этапов; этап — это либо обычная функция, либо запуск
агента в харнессе. Свободный цикл одного «умного» агента на всю задачу плохо измеряется и
плохо проверяется, поэтому порядок этапов задаёт код, а внутри этапа работает агент.

## 3. Харнесс

| Понятие | Что это |
|---|---|
| Агент | данные: имя, системный промпт, список инструментов, требования к модели, бюджет |
| Инструмент | имя, описание, схема входа, обработчик, класс побочного действия (нет / чтение / запись) |
| Прогон | журнал событий, в который только дописывают: сообщения, вызовы инструментов, результаты |
| Шаг | часть прогона до паузы: шаг заканчивается вопросом автору или итогом |

Правила харнесса:

- **Журнал только дописывается.** Историю не редактируют и не сжимают на лету. Этого требуют
  облачные API для повтора «размышлений» модели, и это же даёт воспроизведение и трассировку.
- **Пауза — штатная операция.** Вопрос автору — это вызов инструмента, который останавливает
  прогон. Состояние сохраняет сервер, харнесс между шагами ничего не помнит.
- **Нейтральный формат сообщений**: текст, вызов инструмента, результат инструмента. Адаптер
  провайдера переводит его в свой формат; «сырые» блоки провайдера возвращаются ему как были.
- **Бюджет задан явно**: число ходов, токены, число раундов вопросов, время. Исчерпан бюджет —
  прогон завершается предсказуемо, с тем, что успел.
- **Ошибка инструмента возвращается модели**, а не роняет прогон: неверный вход — это
  результат с признаком ошибки, модель исправляется сама.
- **Уровни совместимости моделей**: (1) вызов инструментов; (2) только ответ по схеме —
  инструмент выбирается полем в JSON; (3) только текст — модель годится для этапов без
  инструментов. Агент объявляет минимальный уровень.

Перенос в чужие харнессы (после того как свой готов): инструменты и знания — MCP-сервером,
промпт и порядок работы — skill-файлом для распространённых агентных сред. Обратное
направление уже есть: чужой харнесс подключается к серверу по протоколу шага.

## 4. Конвейер проверки

| № | Этап | Кто делает | Результат |
|---|---|---|---|
| 0 | Разбор документа | код | разделы и абзацы с постоянными якорями (`§3.2 ¶4`) |
| 1 | Выделение требований | модель по схеме | атомарные требования: текст, тип, якорь, участники, сущности, числа и единицы; глоссарий |
| 2 | Проверки, параллельно | код + модель | кандидаты в замечания и в вопросы, каждый с якорями |
| 3 | Верификация | код + модель-критик | подтверждённые замечания; сомнительные стали вопросами |
| 4 | Уточнение | автор | ответы; затронутые замечания проверяются заново |
| 5 | Отчёт | код | замечания, правки формулировок, открытые вопросы, оценка по осям, покрытие |

Проверки этапа 2:

- **Структура**: все ли разделы шаблона есть и не пусты.
- **Качество формулировки** каждого требования по признакам ISO/IEC/IEEE 29148: однозначно,
  проверяемо, атомарно, полно, выполнимо. Часть ловится без модели: слова-маркеры («быстро»,
  «удобно», «и т. д.», «при необходимости»), число без единицы, действие без исполнителя,
  «уточнить позже».
- **Согласованность** между требованиями: противоречия, дубли, одна сущность под разными
  именами, ссылки на то, что нигде не определено. Кандидатные пары даёт поиск по требованиям,
  а не перебор всех со всеми.
- **Покрытие предметной области**: по типу продукта (платежи, кредиты, идентификация клиента,
  карты) отбираются применимые правила из базы знаний, и для каждого решается: покрыто,
  покрыто частично, не покрыто, неприменимо.

## 5. Знания и RAG

Три корпуса с разным уровнем доверия:

| Корпус | Содержимое | Для чего |
|---|---|---|
| **Документ** | проверяемое ТЗ и ответы автора, по абзацам с якорями | доказать «этого в тексте нет», проверить «ответ уже есть в тексте», найти пары на противоречие |
| **Нормы** | шаблон ТЗ организаторов, стандарты на требования и на ТЗ, отраслевые и регуляторные требования | текст, на который разрешено ссылаться |
| **Правила** | наши атомарные чек-листы, выведенные из норм | что именно проверять и как |

Правило — запись с полями: идентификатор, утверждение («ТЗ на денежную операцию определяет
поведение при повторной отправке запроса»), условие применимости (теги продукта), источники в
корпусе норм, важность по умолчанию, шаблон вопроса автору, способ проверки. Правила — главный
актив: их можно читать глазами, версионировать и покрывать тестами.

Поэтому «RAG» здесь — два разных механизма:

1. **Отбор правил** — по тегам применимости, детерминированно. Каждое применимое правило
   обязано получить вердикт, отсюда метрика покрытия.
2. **Поиск фрагментов** — в документе и в нормах, гибридный: по словам (BM25) и по смыслу
   (эмбеддинги), слияние рангов, при необходимости переранжирование.

Пайплайн: разбор → нормализация → нарезка по структуре (раздел, абзац, строка таблицы; не по
числу символов) → метаданные (источник, версия, дата, юрисдикция, раздел) → индекс → поиск →
ответ с обязательным идентификатором фрагмента → проверка цитаты.

Правила RAG:

- Нет идентификатора фрагмента — нет ссылки на норму. Модель не цитирует законы по памяти.
- Найденный текст — данные, а не инструкции.
- Эмбеддинги идут через шлюз, как и остальные модели; для русского и казахского нужна
  многоязычная модель, она же должна работать on-premise.
- Хранилище за портом: для хакатона достаточно файла (SQLite с полнотекстовым поиском и
  векторами); в контуре банка подменяется на их базу без правок выше.

Источники для корпуса норм — кандидаты, которые надо отобрать и сверить по первоисточникам:
шаблон организаторов; ISO/IEC/IEEE 29148 и ГОСТ 34.602 (структура и качество ТЗ); законы
Казахстана о персональных данных, о противодействии отмыванию доходов, о платежах и платёжных
системах; требования регулятора к информационной безопасности; PCI DSS; OWASP ASVS. Точные
редакции и применимость я не сверял.

## 6. Верификация

Замечание-кандидат проходит ворота по порядку. Первые два — без модели.

| № | Ворота | Как | Не прошло |
|---|---|---|---|
| 1 | Цитата существует | текст цитаты найден по якорю после нормализации пробелов и кавычек | отбросить |
| 2 | Ссылка на норму существует | идентификатор фрагмента есть в базе, процитированное совпадает | убрать ссылку или отбросить |
| 3 | «В тексте этого нет» | целевой поиск темы по документу; находки судит критик | отбросить, если тема раскрыта |
| 4 | Критик | другая роль, по возможности другая модель; видит замечание и доказательства, задача — опровергнуть | опровергнуто → отбросить; не уверен → вопрос автору |
| 5 | Слияние и важность | дубли объединяются; важность ставится по шкале последствий | — |

Шкала важности: **критично** — по ТЗ нельзя начинать разработку либо есть регуляторный или
денежный риск; **существенно** — приведёт к переделке; **незначительно** — формулировка.

Ворота для вопроса автору:

1. ответа нет ни в ТЗ, ни в прошлых ответах (проверяется поиском и попыткой ответить по тексту);
2. указано, что изменится в оценке от ответа;
3. один вопрос — одна неизвестная;
4. не повторяет прошлые раунды;
5. в раунд идут первые N по ожидаемой пользе; остальные ждут или уходят в открытые.

После ответов: ответ становится доказательством со своим якорем; затронутые замечания
проходят ворота заново; противоречие между ответом и текстом ТЗ — само по себе замечание.

Всё отброшенное остаётся в журнале с причиной: по нему считается качество самих ворот.

## 7. Измерение

**Эталонный набор.** Основа — мутации: берём хорошее ТЗ и вносим дефект известного типа в
известное место (удалить раздел, заменить порог словом «быстро», вставить противоречащее
требование, переименовать сущность в одном месте, убрать требование к аутентификации). Каждая
мутация даёт размеченный пример автоматически. Плюс чистые ТЗ для подсчёта ложных
срабатываний, несколько размеченных вручную и шаблон организаторов, когда придёт.

**Автор-симулятор.** Модель, которая знает исходное ТЗ без дефекта и отвечает на вопросы
агента. Это позволяет мерить диалог уточнения целиком, без человека.

| Что меряем | Метрика | Тип порога |
|---|---|---|
| Замечания | полнота по внесённым дефектам, по типам | не хуже базового прогона |
| Замечания | точность; ложные срабатывания на чистом ТЗ | не хуже базового прогона |
| Замечания | доля с существующей цитатой; доля с существующей ссылкой на норму | жёстко 100 % |
| Вопросы | доля вопросов, на которые ответ уже есть в тексте | жёсткий потолок |
| Вопросы | доля дефектов «нужно уточнение», по которым задан вопрос; повторы | не хуже базового |
| Диалог | сколько дефектов снято после ответов симулятора | не хуже базового |
| Верификация | сколько верных замечаний убито и сколько ложных пропущено | не хуже базового |
| Поиск | полнота в первых k, точность цитирования | не хуже базового |
| Покрытие | доля применимых правил, получивших вердикт | жёстко 100 % |
| Система | время и стоимость одной проверки, доля сбоев, разброс между тремя прогонами | потолок |

Те же числа по каждой модели (облачной и локальной) — готовая таблица для защиты.

## 8. Гейт

Числа из раздела 7 становятся решением «принять или отклонить». Правила гейта:

1. **Набор кейсов — файл в репозитории.** Кейс — это ТЗ с известными дефектами плюс конфигурация
   прогона. Наборы: `quick` — минуты, во время работы; `full` — перед слиянием в main.
2. **Кандидат определяется содержимым.** Идентификатор кандидата — дерево исходников, версии
   агента, правил и среза знаний, модель. Тот же кандидат на тех же входах не запускается
   повторно: результат берётся из истории. Деньги на модель тратятся один раз.
3. **История только дописывается.** Каждый прогон — строка: время, статус, меры, стоимость,
   контрольная сумма выхода. Ничего не удаляется.
4. **Судим по истории, а не по числу из головы.** База кейса — медиана последних пяти прогонов
   других кандидатов на той же модели. Порог допуска — атрибут кейса или набора.
5. **Меры — потери в процентах, меньше — лучше.** Не «полнота 92 %», а «пропущено дефектов 8 %».
   Тогда правило одно для всех мер: выросло сверх допуска — хуже.
6. **Слова вердикта.** Отказ: `ХУЖЕ ПО КАЧЕСТВУ` (мера выросла), `МЕРА ПРОПАЛА` (перестали
   считать), сбой, таймаут, нарушен жёсткий инвариант. Предупреждение: `МЕДЛЕННЕЕ`, `ДОРОЖЕ`,
   `выход изменился`.
7. **Быстрее или дешевле при худших ответах — это поломка, а не оптимизация.**
8. **Пустой успех — не база.** Прогон, который завершился без ошибок, но не нашёл ничего в ТЗ с
   внесёнными дефектами, считается провалом и в историю как эталон не попадает.
9. **Во время работы — один свой кейс, перед слиянием — полный прогон.** Слияние в main без
   зелёного полного прогона на этом дереве запрещает хук.

Особенности из-за моделей:

- **Два вида кейсов.** *Повтор*: ответы модели записаны заранее, прогон детерминирован,
  контрольная сумма выхода обязана совпасть — так проверяется логика конвейера, бесплатно и за
  секунды. *Живой*: настоящая модель, три повтора, судим медиану мер с допуском; запускается в
  `full` и при любом изменении промпта, правил или модели.
- **Разброс между повторами — тоже мера.** Агент, который на одном ТЗ даёт разные отчёты, хуже.
- **Стоимость вместо памяти**: токены входа и выхода и цена прогона; время — без ожидания очереди.
- **Сравнение только внутри одной модели.** Прогон на другой модели базой не служит.

Меры по слоям — у каждого слоя свои, иначе непонятно, какой слой испортил итог:

| Слой | Меры (потери, %) |
|---|---|
| Разбор документа | потерянный текст; якоря, изменившиеся при повторном разборе |
| Выделение требований | пропущенные требования; лишние; неверный тип |
| Каждая проверка этапа 2 | пропущенные дефекты своего типа; ложные кандидаты |
| Поиск | нужный фрагмент не попал в первые k |
| Ворота верификации | верные замечания, отброшенные воротами; ложные, прошедшие ворота |
| Вопросы | ответ уже был в тексте; повторы; дефекты «нужно уточнение» без вопроса |
| Диалог | дефекты, не снятые после ответов автора-симулятора |
| Отчёт | замечания без существующей цитаты и ссылки без фрагмента (инвариант: 0); применимые правила без вердикта (инвариант: 0) |
| Харнесс | прогоны, не уложившиеся в бюджет; незавершённые; ошибки инструментов |
| Шлюз | неуспешные вызовы; повторы; срабатывания запасного провайдера |
| Система | время; токены; цена; разброс между повторами |
| Код | `make check`: формат, линтеры, тесты, контракт Rust ↔ Python, сквозной прогон |

## 9. Сквозные качества

Требования, которым подчиняется каждый слой. У каждого — способ проверки: качество, которое
нельзя проверить, считается отсутствующим.

### 9.1. Паттерны

| Паттерн | Где | Зачем |
|---|---|---|
| Порты и адаптеры | вокруг ядра: модели, хранилища, инструменты, клиенты | внешняя система меняется без правок логики |
| Конечный автомат | проверка и прогон агента | разрешены только описанные переходы; «зависших» состояний нет |
| Журнал событий | прогон: состояние вычисляется из событий | возобновление после сбоя, аудит, трассировка, вход для метрик |
| Конвейер с типами | этапы проверки | этап — функция от входа; результат кэшируется и проверяется отдельно |
| Оркестратор и исполнители | параллельные проверки этапа 2 | независимые проверки не ждут друг друга |
| Автор и критик | верификация | тот, кто нашёл замечание, не судит его сам |
| Прерывание на человека | вопрос автору | пауза — штатное состояние, а не обходной путь |
| Реестр и декларации | агенты, инструменты, правила, провайдеры | расширение — новый файл данных, а не новый код |
| Нейтральный формат | сообщения и инструменты между харнессом и моделями | провайдер не протекает в логику агента |
| Идемпотентный шаг | протокол шага | повтор после сбоя не удваивает эффект |
| Предохранитель и запасной путь | вызовы моделей | сбойный провайдер отключается, работа идёт через запасного |

### 9.2. Оптимизация

Меряем две величины: время и стоимость одной проверки. Обе входят в метрики раздела 7.

1. **Что можно сделать без модели, делается без модели**: структура, слова-маркеры, проверка
   цитат и ссылок.
2. **Общий неизменный префикс.** Системный промпт, инструменты и текст ТЗ идут первыми и не
   меняются между вызовами, переменная часть — в конце. Тогда кэш промпта срабатывает на всех
   проверках одного документа.
3. **Кэш результатов этапов по содержимому.** Ключ — версия этапа, вход, модель, версия
   правил. После ответов автора пересчитываются только затронутые этапы.
4. **Параллельные проверки с ограничением** числа одновременных вызовов.
5. **Модель под этап** — таблица в конфиге: дешёвая для извлечения, сильная для критика и
   вопросов. Начинаем с одной модели; разводим только там, где метрики показали выигрыш.
6. **Весь документ или поиск** — по размеру контекста модели: большой модели даём ТЗ целиком,
   маленькой локальной — найденные фрагменты.
7. **Поток событий в интерфейс**: замечания появляются по мере работы, а не в конце.

### 9.3. Безопасность

| Угроза | Защита |
|---|---|
| Инструкции для модели внутри ТЗ, норм или ответов автора | текст всегда передаётся как данные; у инструментов нет опасных действий; выход по схеме. Худший исход — ложное замечание, его ловит верификация |
| Конфиденциальное ТЗ уходит в облако | режим «только on-premise»: шлюз отказывает облачным провайдерам на уровне конфига; при гибриде — маскирование персональных данных перед отправкой |
| Чужой расход денег и ресурсов через API | токен, ограничение частоты и размера запроса, бюджет на проверку |
| Утечка секретов | только переменные окружения; в логи не попадают ни ключи, ни текст ТЗ |
| Вредный вывод модели в интерфейсе | вывод модели показывается как текст, разметка экранируется |
| Зависимости | версии зафиксированы, проверка известных уязвимостей входит в общую проверку; сторонние установщики в сборке не запускаются |
| Хранение чужих документов | срок хранения и удаление по запросу; журнал: кто, когда и какой модели передал данные |

Сверка — по списку OWASP Top 10 для приложений на LLM.

### 9.4. Надёжность

1. **Таймаут у каждого внешнего вызова.** Повтор только для временных ошибок, с растущей
   паузой; отказ модели и обрезанный ответ не повторяются вслепую.
2. **Сбой не теряет работу.** Журнал хранится на диске; прогон продолжается с последнего события.
3. **Нет вечного «выполняется».** Шаг держит аренду с отметками; без отметок шаг повторяется
   или помечается сбойным.
4. **Частичный результат объявляется.** Проверка не выполнилась — в отчёте написано, какая и
   почему. Критик недоступен — замечания помечены непроверенными, а не выданы за проверенные.
5. **Выход модели всегда проверяется по схеме.** Починка — не больше двух попыток, дальше
   этап считается сбойным.
6. **Запасной провайдер** задаётся политикой; в режиме «только on-premise» запасной тоже локальный.
7. **Наблюдаемость**: структурные логи, трасса каждой проверки, счётчики времени, токенов и
   ошибок, проверка готовности.
8. **Тесты на сбои**: провайдер отвечает ошибкой, молчит, возвращает мусор — поведение системы
   описано и проверено тестом, как и успешный путь.

### 9.5. Модульность

Модуль — это контракт, реализация, тесты на поддельных соседях и своя метрика.

| Модуль | Контракт | Чем заменяется |
|---|---|---|
| Шлюз моделей | нейтральный запрос и ответ | другой провайдер — секция конфига или адаптер |
| Ядро харнесса | протокол шага, журнал событий | — |
| Инструмент | имя, схема входа, результат; по форме совпадает с MCP | любой сервис на любом языке |
| Агент | файл описания | другой файл |
| Этап и проверка | типы входа и выхода | другая реализация того же типа |
| Ворота верификации | кандидат → вердикт с причиной | добавляются и отключаются по одному |
| Хранилище знаний | поиск → фрагменты с идентификаторами | файл или база заказчика |
| Набор правил | файлы с версией | набор другой предметной области |
| Счётчик метрики | прогон → число | — |
| Клиент | HTTP API | веб, CLI, MCP |

Правила: зависимости только внутрь; модули общаются типами из `contracts/`, а не внутренностями;
у контракта есть версия; модуль проверяется отдельно от остальных.

### 9.6. Адаптивность

| К чему | Как |
|---|---|
| Модель | уровни совместимости; стратегия «весь документ или поиск» по размеру контекста |
| Документ | определение языка, размера и типа продукта выбирает наборы правил; шаблон подключается как данные |
| Предметная область | новая область — новый набор правил, код тот же |
| Автор | вопросы прекращаются, когда ожидаемая польза ниже порога; вопросы можно пропускать |
| Среда | профили: облако, on-premise, гибрид — конфигом |
| Обратная связь | отметка автора «замечание неверно / полезно» попадает в эталонный набор; промпты и правила правятся по метрикам, а не сами собой |
| Чужие харнессы | инструменты и знания через MCP, порядок работы через skills |

Система не меняет собственные промпты и правила без прогона метрик: адаптация — управляемая.

## 10. Правила проекта

Дополняют `CONTRIBUTING.md`, когда начнётся реализация.

1. Изменение промпта, правила, инструмента или модели не принимается без прогона эталонного
   набора; результат прогона сохраняется рядом с изменением.
2. Решение о принятии выносит гейт (раздел 8) по истории прогонов. `ХУЖЕ ПО КАЧЕСТВУ` и
   `МЕРА ПРОПАЛА` — отказ, как упавший тест.
3. Жёсткие инварианты (цитата, ссылка на норму, схема, покрытие) проверяются и при работе:
   нарушение не доходит до пользователя.
4. Каждый отчёт записывает версии: агента, правил, среза базы знаний, модели. Отчёт
   воспроизводим.
5. Идентификаторы правил и якорей постоянны; правило не удаляют, а помечают снятым.
6. Пороги и лимиты — в конфиге, не в коде и не в промпте.
7. Инструмент объявляет свой класс побочного действия; у агента проверки ТЗ — только «нет» и «чтение».
8. Журнал прогона только дописывается и хранится целиком.
9. Новый этап конвейера приходит вместе со своей метрикой и примерами в эталонном наборе.
